## 0. ГЛАВНОЕ

### Философия проекта
> **"Минимум кнопок и текста, максимум полезности и смысла.**
> С пары кнопок я мог получить лид."

Каждый элемент сайта должен пройти **Тест Ценности**:
1. Посетитель может объяснить пользу этого элемента в одном предложении? → Оставляем
2. Без этого элемента можно обойтись? → Удаляем
3. Это мешает быстрому действию (заявка, вопрос)? → Удаляем

### Цель сайта
Сайт-визитка специалиста по продвижению сайтов — не визитка ради визитки, а **машина генерации лидов** с минимальным трением.

## 1. Философия дизайна

### Принцип: Один посетитель → Одна цель
Посетитель приходит за результатом. Сайт должен помочь ему сделать это максимально быстро.

### Правило 3 кликов до лида
Любой посетитель должен получить возможность оставить заявку максимум за **3 действия**:
- Клик по кнопке
- Заполнение формы (или нажатие preset-вопроса в чате)
- Подтверждение

Никаких скроллов, которые не несут ценности. Контакт/CTA — виден сразу или через один клик.

### Принцип: Факты > Обещания
| ❌ Не делать | ✅ Делать |
|---|---|
| «Опытный специалист с индивидуальным подходом» | «10 лет в SEO, 200+ проектов, ТОП-3 Яндекс/Google» |
| «Мы предлагаем комплексные решения» | «Аудит сайта за 24 часа → план работ → результат через 2 недели» |
| Красивые абстрактные фразы | Конкретные кейсы: «Было: 100 визитов/день → Стало: 800» |

### Принцип: Одно действие = одна кнопка
Не более двух primary-кнопок на любом экране. Третья кнопка — уже clutter.

## 2. Золотые правила разработки

### Правило P1: Rust → безопасность по умолчанию
```rust
// ✅ Правильно
match result {
    Ok(value) => /* use value */,
    Err(e) => error!("Failed: {}", e), // или propagate
}

// ❌ Никогда в продакшене
let value = result.unwrap(); // PANIC!
```

- Zero-трюст к внешним данным (все API, все формы)
- Error Handling через `Result`/`Option`, ноль `unwrap()` в продакшене
- Асинхронность через `tokio`, никогда не блокировать event loop
- Все конфигурации — из env/files, ноль хардкода секретов

### Правило P2: Лёгкость — это фича
- Docker-образы: только `alpine`/`slim`/`scratch`
- Нет Node.js на продакшене для фронтенда
- Нет Python-бандлов там, где достаточно Rust
- Каждый слой Docker должен быть оправдан
- Итоговый образ: **< 50MB**

### Правило P3: OpenViking как единый источник правды
Всё, что знает сайт об авторе (навыки, проекты, статусы, контакты) — хранится в OpenViking (`viking://` URIs).
- Нет дублирующих баз
- Нет хардкода фактов о себе
- Chatbot спрашивает OpenViking → отвечает актуально

### Правило P4: Данные → Инсайты → Действия
Каждый собранный данные (чаты, просмотры, лиды) должен превращаться в полезную метрику.
- Если данные собираются, но не анализируются — они мусор и удаляются
- Каждый день — сводка: лиды, конверсии, топ-вопросы

### Правило P5: Конфиденциальность — не обсуждается
- Все чаты шифруются при хранении
- Контакты посетителей не передаются третьим лицам
- Админ-панель защищена token-аутентификацией
- Логирование без персональных данных в открытом виде

### Правило P6: Минимум зависимостей
```toml
# ✅ Пример Cargo.toml с минимальным количеством фреймворков
[dependencies]
leptos = { version = "0.6", features = ["ssr"] }
tokio = { version = "1", features = ["full"] }
hyper = { version = "1", features = ["server", "http1"] }
serde = { version = "1", features = ["derive"] }
# Только то, что реально нужно. Ничего лишнего.
```

### Правило P7: Тестирование по умолчанию
- Все API-эндпоинты покрыты unit-тестами
- Логика чатбота тестируется через mock-providers
- CI-пайплайн обязателен перед merge в main

## 3. Роль специалиста на сайте

### Позиционирование
```
Специалист по продвижению сайтов с 10-летним опытом
Помогаю бизнесу получать клиентов из поисковых систем
```

### Ключевые метрики (примеры, адаптировать под реальные):
| Показатель | Значение |
|---|---|
| Опыт в SEO | 10+ лет |
| Проектов завершено | 200+ |
| Средняя конверсия клиентов | +340% за первые 3 месяца |
| Текущих проектов | 5-7 (активная загрузка) |
| Средний чек проекта | от 50 000 ₽ |

### Целевая аудитория
1. **Владельцы бизнеса** — у них есть сайт, но нет заявок из поиска
2. **Маркетологи** — им нужен SEO-эксперт для совместной работы
3. **Разработчики** — им нужен SEO-оптимизированный сайт

### Тон коммуникации
- Деловой, но не сухой
- Конкретика вместо воды
- Уверенность без высокомерия
- Готовность помочь (чат бот всегда доступен)

## 5. Стек технологий

| Компонент | Технология | Почему |
|---|---|---|
| Фронтенд | **Leptos** (Rust) | SSR, компиляция в WASM/HTML, минимальный бандл |
| Бэкенд API | **Hyper + tokio** (Rust) | Native-скорость, async, zero-cost абстракции |
| Контейнеризация | **Docker** (multi-stage) | Минимальный образ (~30-50MB) |
| База чатов | **SQLite** (WAL mode) | Лёгкая, SQLx драйвер для Rust |
| Память ИИ | **OpenViking** (`viking://`) | Семантический поиск по знаниям об авторе |
| LLM API | **DeepSeek V4** (OpenAI-compatible) | Хорошее соотношение цена/качество |
| Уведомления | **Telegram Bot API** + **VK API** | Мгновенные лиды в мессенджеры |

## 6. Контекстная память ИИ

### Хранение в OpenViking (`viking://`)
Все знания о специалисте хранятся как URI-ресурсы:

```
viking://user/inteli-dev/profile/     — профиль автора
viking://user/inteli-dev/projects/    — проекты и кейсы
viking://user/inteli-dev/services/    — услуги и цены
viking://user/inteli-dev/policies/    — статусы и доступность
viking://user/inteli-dev/prompts/     — системные промпты для chatbot
```

### Поиск по памяти
AI-чатбот использует три режима:
1. **find(uri)** — поиск по конкретной коллекции (например, услуги)
2. **search(query)** — семантический поиск по всей базе
3. **grep(patterns)** — точный поиск по тексту (цены, контакты)

### Обновление памяти
- Автор обновляет данные через админ-панель → запись в OpenViking
- Public API читает из OpenViking → кэширует на 1 час в Redis
- Статус занятости проверяется в реальном времени из OpenViking
