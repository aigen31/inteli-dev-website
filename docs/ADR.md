# Architecture Decision Records (ADR)

Ключевые архитектурные решения проекта inteli-dev.ru. Каждое решение фиксирует
контекст, выбор, альтернативы и последствия.

---

## ADR-001: Leptos SSR без hydration + ванильный JS для интерактивности

- **Статус:** Accepted
- **Контекст:** Сайт-визитка — это контентные страницы (SEO-оптимизация) плюс
  ограниченная интерактивность (чат, форма). Правила требуют Leptos + «лёгкость»
  и «минимум зависимостей» (P2, P6).
- **Решение:** Leptos используется только для SSR (feature `ssr`, без `hydrate`/
  WASM). Интерактивность чата и формы реализована ванильным JS (`assets/main.js`),
  который ходит в JSON API (`/api/chat`, `/api/lead`).
- **Альтернативы:**
  - Полная гидрация (Leptos + WASM через trunk/wasm-bindgen) — точная интерактивность,
    но добавляет тулчейн WASM и увеличивает бандл.
  - Чистый static HTML — теряет серверный рендер из OpenViking.
- **Последствия:**
  - (+) SSR для SEO-страниц, один бинарник, малый бандл, нет WASM-тулчейна.
  - (−) Интерактивность на JS, не на Leptos-сигналах; при росте сложности UI стоит
    вернуться к гидрации.

## ADR-002: axum (hyper-based) вместо «сырого» hyper

- **Статус:** Accepted
- **Контекст:** Правила упоминают «Hyper + tokio». Leptos 0.7 интегрируется с axum
  через `leptos_axum`.
- **Решение:** Использовать axum 0.7 (построен поверх hyper) как HTTP-слой.
- **Альтернативы:** сырой hyper — больше ручного кода, нет extractors/middleware.
- **Последствия:** (+) extractors (`State`, `Json`, `Path`, `Query`), единый Router для
  API + SSR + статики. (−) axum добавляет небольшой слой поверх hyper.

## ADR-003: In-memory кэш вместо Redis на MVP (Redis = этап P7)

- **Статус:** Accepted
- **Контекст:** Redis в правилах отмечен как низкий приоритет (P7). Для MVP нужен кэш
  ответов LLM и rate limiting.
- **Решение:** `InMemoryCache` (TTL) и `RateLimiter` в одном процессе; интерфейс изолирован
  в `src/cache.rs`, чтобы позже подставить Redis без изменения бизнес-логики.
- **Альтернативы:** сразу Redis (`redis` crate) — ещё одна зависимость и сервис на старте.
- **Последствия:** (+) меньше зависимостей, работает без внешних сервисов. (−) кэш не
  переживает рестарт и не шарится между репликами — приемлемо для одного контейнера.

## ADR-004: Runtime-проверяемые sqlx-запросы вместо `query!` макросов

- **Статус:** Accepted
- **Контекст:** Правила используют `sqlx::query!`, который требует БД на этапе компиляции
  (или `.sqlx` offline-данные). Это усложняет Docker-сборку и CI.
- **Решение:** Использовать `sqlx::query`/`query_as` + `#[derive(FromRow)]` (проверка в
  рантайме). Безопасность сохраняется: только bind-параметры, никакой интерполяции SQL.
- **Альтернативы:** `query!` с offline-режимом — требует поддержания `.sqlx` данных.
- **Последствия:** (+) сборка без DATABASE_URL, проще CI. (−) опечатки в именах колонок
  ловятся в рантайме/тестах, а не на компиляции.

## ADR-005: Метки времени как RFC3339 TEXT (без chrono-колонок sqlx)

- **Статус:** Accepted
- **Контекст:** SQLite хранит даты как TEXT; `CURRENT_TIMESTAMP` даёт формат
  `YYYY-MM-DD HH:MM:SS`, который не всегда разбирается `chrono::DateTime` из sqlx.
- **Решение:** Записывать `chrono::Utc::now().to_rfc3339()` в TEXT-колонки и читать их
  как `String` (парсить при необходимости). Схема по-прежнему совместима с правилами.
- **Последствия:** (+) детерминированный формат, нет сюрпризов декодинга. (−) сравнения
  по датам делаются через SQLite `date()` / в коде, а не через тип.

## ADR-006: Builder-образ `rust:latest` (full, не slim)

- **Статус:** Accepted
- **Контекст:** `sqlx` с `sqlite` тянет `libsqlite3-sys` (bundled), которому нужен
  C-компилятор. `rust:1.84-slim` (debian slim) не содержит gcc, а современные
  транзитивные зависимости (edition 2024) требуют Rust >= 1.85.
- **Решение:** Использовать `rust:latest` (buildpack-deps, есть gcc) для builder.
  Runtime-образ остаётся `alpine:3.20` (~35 MB), т.е. целевой размер не страдает.
- **Последствия:** (+) надёжная сборка SQLite + совместимость с новыми крейтами.
  (−) чуть более тяжёлый builder-слой (только на этапе сборки).

## ADR-008: Точное закрепление версий Leptos (`=0.7.8`)

- **Статус:** Accepted
- **Контекст:** При `leptos = "0.7"` Cargo подтянул `leptos` 0.7.8, но `leptos_macro`
  0.7.9 (лептос 0.7.9 был отозван), что давало несовместимый код роутера
  (`&str: PossibleRouteMatch`). Кроме того, в leptos_router 0.7 маршрут задаётся
  макросом `path!("/")`, а не строковым литералом.
- **Решение:** Закрепить `leptos`, `leptos_axum`, `leptos_router` и `leptos_macro`
  на `=0.7.8`; пути маршрутов писать через `path!()`.
- **Последствия:** (+) воспроизводимая сборка, согласованные макросы и рантайм.
  (−) нужно вручную обновлять все четыре крейта вместе при апгрейде Leptos.

## ADR-007: Fallback-контент при недоступности OpenViking

- **Статус:** Accepted
- **Контекст:** OpenViking — источник правды, но в dev/деградации может быть недоступен.
  Сайт не должен падать.
- **Решение:** `SiteContent::load` пробует OpenViking, при ошибке использует встроенный
  `fallback_content()`. Владелец меняет данные через OpenViking/админку, а не в коде.
- **Последствия:** (+) сайт всегда рендерится. (−) встроенные значения нужно держать в
  актуальном состоянии до подключения OpenViking.
