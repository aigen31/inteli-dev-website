# Статьи блога и кросспостинг через n8n

Статьи — это контент сайта, который **пишется в админке** и **отдаётся наружу
для кросспостинга**. Реализована первая часть (блог + админка + ленты), вторая
заложена архитектурно: публикация статьи порождает событие, которое забирает
n8n. Сам пайплайн n8n в этом репозитории не собирается — здесь только та
сторона, которая должна быть готова заранее.

---

## 1. Что уже работает

| Возможность | Где |
|---|---|
| Публичный блог: список статей | `GET /blog` |
| Публичная страница статьи | `GET /blog/{slug}` (404 для черновиков) |
| RSS-лента с полным текстом | `GET /rss.xml`, `GET /feed.xml` |
| Карта сайта со статьями | `GET /sitemap.xml` |
| Тизер последних статей на главной | блок «Последние статьи» |
| Создание, правка, публикация, удаление | админка → «Статьи блога» |
| Предпросмотр markdown | кнопка «Предпросмотр» в редакторе |
| Outbox событий для n8n | таблица `article_events` + `GET /api/integrations/outbox` |
| Журнал событий в админке | раздел «Кросспостинг» |

Черновики и архив **не попадают** ни на сайт, ни в RSS, ни в карту сайта:
страницы и ленты строятся из снимка `PublishedArticles`, куда попадают только
опубликованные статьи.

---

## 2. Как пользоваться админкой

1. Откройте `/admin`, введите `ADMIN_TOKEN`.
2. Раздел **«Статьи блога»** → «Новая статья».
3. Заполните заголовок и текст в Markdown. Остальное опционально.

| Поле | Обязательное | Правила |
|---|---|---|
| Заголовок | да | до 200 символов |
| Текст (Markdown) | да | до 200 000 символов |
| Краткое описание | нет | до 500 символов; идёт в список, RSS и `<meta description>` |
| Адрес (slug) | нет | пусто — сгенерируется из заголовка транслитом |
| Теги | нет | через запятую, до 10 штук, до 40 символов каждый |
| Обложка | нет | `https://…` или локальный путь `/img/…` |
| Канонический адрес | нет | если статья уже опубликована в другом месте |
| Статус | да | `draft` / `published` / `archived` |

**Статусы и что они значат для кросспостинга:**

| Переход | Событие | Что делает n8n |
|---|---|---|
| черновик → опубликована | `article.published` | постит в каналы |
| опубликована → правка | `article.updated` | обновляет пост (или игнорирует) |
| опубликована → черновик/архив | `article.unpublished` | снимает/помечает пост |
| удаление опубликованной | `article.deleted` | снимает пост |
| черновик → черновик | события нет | ничего: кросспостить нечего |

Кнопка **«Снять»** возвращает статью в черновики, а не в архив: почти всегда
нужно доработать текст, а не отложить его навсегда.

Slug генерируется транслитом кириллицы (`Как я собирал AI-сервер` →
`kak-ya-sobiral-ai-server`), при коллизии добавляется суффикс `-2`, `-3`.
Мягкий и твёрдый знаки выпадают и дефис не создают (`статья` → `statya`, а не
`stat-ya`).

## 3. Архитектура кросспостинга

### 3.1. Направление: сайт → n8n

Сайт — **источник правды**. n8n — потребитель. Сайт не знает адреса n8n и не
ходит к нему: доставка построена на **pull**-модели.

```
   Админка                    SQLite                     n8n
      │                          │                        │
      │  1. publish              │                        │
      ├─────────────────────────►│                        │
      │     [одна транзакция]    │                        │
      │     • UPDATE articles    │                        │
      │     • INSERT article_events (pending)             │
      │                          │                        │
      │  2. reload_published     │                        │
      ├─────────────────────────►│                        │
      │     ▼                    │                        │
      │  снимок в памяти → /blog, /rss.xml, /sitemap.xml  │
      │                          │                        │
      │                          │  3. GET /api/integrations/outbox
      │                          │◄───────────────────────┤
      │                          ├───────────────────────►│  события + payload-снимок
      │                          │                        │
      │                          │  4. постинг в Telegram/VK/Habr
      │                          │                        │
      │                          │  5. POST .../ack       │
      │                          │◄───────────────────────┤
      │                          │   status = delivered   │
```

### 3.2. Почему transactional outbox

Событие пишется **в той же транзакции**, что и сама статья
(`storage/article.rs`). Поэтому состояния «статья опубликована, но событие
потерялось» не существует по построению — а именно так ломается наивная
реализация «сначала записали статью, потом дёрнули вебхук».

Если бы сайт вместо этого сразу звал n8n, то падение сети между записью и
вызовом давало бы либо потерянный пост, либо, при ретрае, дубль.

### 3.3. Два канала

| Канал | Когда использовать | Что отдаёт |
|---|---|---|
| **Outbox** (`/api/integrations/outbox`) | Основной. Точные события: публикация, правка, снятие, удаление | снимок статьи + тип события |
| **RSS** (`/rss.xml`) | Если нужен простой сценарий на RSS Feed Trigger | все опубликованные, полный текст в `content:encoded` |

Outbox предпочтительнее: он сообщает **что именно произошло**, а не «вот
текущее состояние». RSS не умеет рассказать про удаление статьи.

## 4. API для n8n

### Авторизация

Ключ передаётся в заголовке `X-Api-Key`. Источник — env `N8N_API_KEY`.

```bash
# Сгенерировать ключ
openssl rand -hex 32
```

Пока ключ не задан, **все** эндпоинты `/api/integrations/*` отвечают `404`.
Это осознанный fail-closed: незащищённый фид, отдающий черновики, хуже
отсутствующего фида. При неверном ключе — `401`.

### `GET /api/integrations/outbox`

| Параметр | По умолчанию | Значение |
|---|---|---|
| `status` | `pending` | `pending` / `delivered` / `failed` |
| `limit` | `outbox_batch_limit` из конфига | 1…500 |

```bash
curl -s -H "X-Api-Key: $N8N_API_KEY" \
  "https://inteli-dev.ru/api/integrations/outbox?status=pending&limit=20"
```

```json
{
  "events": [
    {
      "id": 12,
      "article_id": 4,
      "slug": "kak-ya-sobiral-ai-server",
      "event_type": "article.published",
      "status": "pending",
      "attempts": 0,
      "created_at": "2026-09-24T12:00:00+00:00",
      "delivered_at": null,
      "last_error": null,
      "payload": {
        "article": {
          "id": 4,
          "slug": "kak-ya-sobiral-ai-server",
          "url": "https://inteli-dev.ru/blog/kak-ya-sobiral-ai-server",
          "title": "Как я собирал AI-сервер",
          "summary": "Краткое описание",
          "body_markdown": "# Заголовок\n\nТекст статьи.",
          "cover_image_url": null,
          "tags": ["gpu", "ai"],
          "status": "published",
          "published_at": "2026-09-24T12:00:00+00:00",
          "updated_at": "2026-09-24T12:00:00+00:00",
          "reading_time_minutes": 4,
          "canonical_url": null
        }
      }
    }
  ],
  "count": 1,
  "base_url": "https://inteli-dev.ru"
}
```

`payload` — **снимок** статьи на момент события, а не ссылка на id. К моменту,
когда n8n заберёт событие, статью могли переписать или удалить, а кросспостить
нужно то, что было опубликовано.

### `POST /api/integrations/outbox/ack`

```json
{ "ids": [12, 13] }
```

Ответ: `{ "acked": 2 }` — сколько событий реально перешло в `delivered`.

**Идемпотентно.** Повторный вызов ничего не сломает и вернёт `acked: 0`,
поэтому n8n может переподтвердить весь батч после сетевого сбоя.

### `POST /api/integrations/outbox/fail`

```json
{ "id": 12, "error": "502 от n8n" }
```

Инкрементирует `attempts`. После **5** попыток событие уходит в `failed` и
перестаёт выдаваться в `pending`. Это защита от «отравленного» события, которое
вечно роняет пайплайн: разбирать `failed` нужно руками.

### Заготовка workflow в n8n

```
[Schedule Trigger: каждые 5 минут]
        │
        ▼
[HTTP Request: GET /api/integrations/outbox?status=pending]
  Header: X-Api-Key = {{$credentials.n8nApiKey}}
        │
        ▼
[Split In Batches: 1]
        │
        ▼
[Switch: {{$json.event_type}}]
   ├── article.published  → [HTTP: Telegram sendMessage / VK wall.post] → [Set: id]
   ├── article.updated    → [обновить пост]                              → [Set: id]
   ├── article.unpublished→ [удалить/пометить]                           → [Set: id]
   └── article.deleted    → [удалить]                                    → [Set: id]
        │
        ▼
[Aggregate: собрать id]
        │
        ▼
[HTTP Request: POST /api/integrations/outbox/ack  { "ids": [...] }]

     при ошибке ноды постинга:
[HTTP Request: POST /api/integrations/outbox/fail { "id": ..., "error": ... }]
```

Ключ хранить в n8n как **Credential** (Header Auth), а не в тексте ноды.

## 5. Модель данных

### `articles`

| Колонка | Тип | Назначение |
|---|---|---|
| `id` | INTEGER PK | |
| `slug` | TEXT UNIQUE | адрес на сайте |
| `title` | TEXT | заголовок |
| `summary` | TEXT | краткое описание |
| `body_markdown` | TEXT | тело статьи |
| `cover_image_url` | TEXT NULL | обложка |
| `tags` | TEXT | JSON-массив строк |
| `status` | TEXT | `draft` / `published` / `archived` (CHECK) |
| `published_at` | TEXT NULL | момент публикации |
| `created_at`, `updated_at` | TEXT | RFC3339 |
| `source` | TEXT | `admin` / `n8n` / `import` (CHECK) |
| `external_id` | TEXT NULL | ключ идемпотентности внешнего источника |
| `canonical_url` | TEXT NULL | если материал уже где-то опубликован |

`source` + `external_id` — задел под обратное направление (n8n сам создаёт
статьи). Уникальный индекс `idx_articles_external` не даст повторному прогону
импорта создать дубль.

### `article_events` (outbox)

| Колонка | Назначение |
|---|---|
| `id` | PK |
| `article_id`, `article_slug` | что изменилось |
| `event_type` | `article.published` / `updated` / `unpublished` / `deleted` (CHECK) |
| `payload` | JSON-снимок статьи |
| `status` | `pending` / `delivered` / `failed` (CHECK) |
| `attempts` | число неудачных попыток |
| `next_attempt_at` | задел под push-доставку с backoff |
| `created_at`, `delivered_at`, `last_error` | журнал |

`article_id` **не** объявлен как FOREIGN KEY сознательно: это неизменяемый лог
доставки, он обязан переживать удаление статьи — событие `article.deleted`
должно дойти до читателя, когда строки статьи уже нет.

## 6. Markdown и безопасность

Тело статьи — Markdown, рендерится `pulldown-cmark` в `src/utils/markdown.rs`.
Включены таблицы, зачёркивание, чек-листы, сноски, типографские кавычки.

Один рендерер на всё приложение: страница статьи, RSS и предпросмотр в админке
используют его же, поэтому предпросмотр не может разойтись с публикацией.

**Сырой HTML экранируется** — `<script>` из текста становится текстом.
Ссылки с опасными схемами (`javascript:`, `vbscript:`, `data:`) заменяются на
`#`. Это не паранойя: через этот же рендерер пойдут статьи, пришедшие из n8n.

В RSS полный HTML заворачивается в `CDATA`, а `]]>` внутри разрывается на две
секции — вырваться из CDATA и дописать свой XML статья не может.

## 7. Конфигурация

```toml
[server]
# Публичный адрес: абсолютные ссылки в RSS, sitemap, событиях.
public_url = "https://inteli-dev.ru"

[integrations]
# Ключ фида событий. Пусто — фид выключен (404).
n8n_api_key = ""
# Сколько событий отдавать за один запрос.
outbox_batch_limit = 50
```

Env-переопределения: `PUBLIC_URL`, `N8N_API_KEY`.

На локальной проверке `PUBLIC_URL` стоит `http://127.0.0.1:8282`, иначе ссылки
в RSS и событиях вели бы на прод.

## 9. Что дальше (когда дойдёт до n8n)

1. Сгенерировать `N8N_API_KEY`, положить в `.env.prod` и `docker compose up -d`.
2. Собрать workflow по схеме из §4.
3. Обратную сторону (`source = 'n8n'`, `external_id`) включить, если понадобится
   импорт статей извне: колонки и уникальный индекс уже есть, нужен только
   приёмный эндпоинт.
4. Push-доставку (n8n Webhook-нода вместо опроса) добавить поверх той же схемы:
   `attempts` и `next_attempt_at` уже есть, миграция не потребуется.

## 10. Проверка

```bash
# Юнит- и интеграционные тесты
cargo test

# Лента
curl -s https://inteli-dev.ru/rss.xml | head -30

# Фид событий (ключ обязателен)
curl -s -H "X-Api-Key: $N8N_API_KEY" \
  https://inteli-dev.ru/api/integrations/outbox | jq
```

Тесты блога помечены в `tests/api.rs` секцией «Статьи блога и кросспостинг» и
берут общий замок: `PublishedArticles` — глобальный снимок в памяти, а тесты
одного бинарника идут параллельно.
