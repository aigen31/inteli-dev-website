## Основной принцип хранения

> **"Один источник правды — одна система для одного типа данных."**

Каждый тип данных хранится в единственном месте:
- Контент сайта (профиль, услуги, кейсы) → **код** (`src/memory/content.rs`)
- История чатов → **SQLite**
- Заявки/лиды → **SQLite** + уведомление через API
- Живой статус занятости → **SQLite** (`site_settings`)
- Прайс-лист → **SQLite** (`prices`)
- Статьи блога → **SQLite** (`articles`)
- Кэш ответов LLM → **Redis** (или in-memory кэш в dev)
- Статические файлы и иллюстрации → **файловая система** (`/assets`)

## Где что лежит

| Данные | Хранилище | Кто пишет | Кто читает |
|---|---|---|---|
| Профиль, услуги, кейсы | `src/memory/content.rs` | разработчик, релиз | UI, чат, MCP |
| Статус занятости | SQLite `site_settings` | Telegram-бот, админка | бейдж, `/api/status`, чат |
| Прайс | SQLite `prices` | админка | чат, MCP |
| Лиды | SQLite `leads` | форма, чат | админка, уведомления |
| Чаты | SQLite `chats` | чат | админка |
| Статьи | SQLite `articles` | админка | блог, RSS, фид событий |
| Кэш ответов | Redis / in-memory | сервис чата | сервис чата |

### Почему контент в коде

Контент описывает позиционирование: кто автор, что продаёт, какие кейсы
показывает. Он меняется вместе с релизом, проверяется тестами и не требует
сети на старте. Живые данные, которые меняются несколько раз в день, для этого
не годятся — они лежат в SQLite и правятся без пересборки.

### Почему статус в SQLite

Статус занятости — состояние сервиса, а не контент. Он должен переживать
рестарт и записываться, когда владелец нажимает кнопку в Telegram. Поэтому
`site_settings` (ключ → JSON) рядом с заявками, а `SiteContent.availability`
работает только как значение по умолчанию, пока записи нет.

## Форматы и схема

### Таблица `site_settings`

```sql
CREATE TABLE site_settings (
    key        TEXT PRIMARY KEY,
    value      TEXT NOT NULL,          -- JSON
    updated_at TEXT NOT NULL
);
```

Ключ `availability` хранит `{"status": "...", "current_projects": N, ...}`.
Валидация одна на два входа (бот и админка): `apply_command`.

### Таблица `prices`

Строки прайса: направление, название пакета, цена от/до, валюта. На первом
запуске таблица заполняется диапазонами из услуг контента, дальше правится в
админке. Ассистент читает её через MCP.

### Таблица `leads`

Заявки: имя, контакты, сообщение, источник, статус, отметка согласия на
обработку данных, временные метки. Статусы: `new` → `in_progress` → `done`.

### Таблица `chats`

История диалогов: сессия, роль, текст, источник ответа. Источники:
`direct` (ответ из контента), `llm`, `llm_fallback`, `cached`.

## Стратегии кеширования

| Что | TTL | Инвалидация |
|---|---|---|
| Ответы чата | 1 час | смена статуса или прайса |
| Счётчики GitHub | 1 час | по TTL |
| Статика | версионирование в имени файла | новый релиз |

Кэш ответов — оптимизация, а не источник правды: при промахе ответ собирается
заново из контента и БД.

## Бэкапы

| Данные | Как | Частота | Хранение |
|---|---|---|---|
| SQLite (`chats.db`) | `sqlite3 chats.db ".backup chats.db.full"` | ежедневно | 7 дней локально |
| Конфиг без секретов | git | при изменении | репозиторий |
| Секреты | `.env.prod` на сервере | по необходимости | вне git |

Восстановление: остановить `web`, положить файл БД на место тома `db-data`,
поднять `web`. Схема догоняется миграциями при старте.
